# Person Re-ID v1 — Map

Labels: wayfinder:map

Spec: [spec.md](spec.md) (Status: ready-for-agent)

## Destination

A buildable spec for Re-ID v1: a Python (uv-packaged) Docker container on the Pi 5 that, on nightly manual/batch runs, detects persons, stores embeddings incrementally (wipeable via UI), rebuilds clusters from scratch each run within a configurable timespan window (default: same calendar day), anchors clusters via Immich face labels, and proposes name assignments — confirmed through a small web UI with dry-run mode before anything is written back to Immich. Ready for `/to-spec`.

## Notes

- `goal.md` at the repo root is the source idea; read it first.
- Single user. Immich runs on a Raspberry Pi 5 (CPU-only, ARM64) on the local network; the Re-ID container targets the same Pi.
- Python throughout; Astral's `uv` as package manager.
- Nightly manual/batch trigger. Embeddings are stored incrementally (new photos only) with UI buttons to erase the store; cluster assignments are rebuilt from scratch every run.
- The timespan window is a configurable parameter, default same calendar day.
- Immich face labels are ground truth, taken as-is in v1. Human confirmation is required before any write-back; dry-run mode exists from day one.
- The assumption "every cluster contains at least one Immich-recognized face" is a prediction to validate with real data; anchor-less clusters get an ask-for-name fallback in the UI.
- Skills per ticket type: grilling tickets run `grilling` + `domain-modeling`; research tickets run `research`; the prototype ticket runs `prototype`.

## Decisions so far

<!-- the index: one line per closed ticket, enough to judge relevance, then zoom the link for the detail the ticket holds -->

- [Immich API surface](issues/01-immich-api-surface.md): All four pipeline needs are served: new assets via `POST /search/metadata` (`createdAfter`) or the checkpointed `POST /sync/stream` feed; per-asset face detections with pixel boxes via `GET /faces?id=<assetId>` (the param is the asset ID despite misleading spec docs; returns **all** detections including unassigned, `person: null` — corrected 2026-11-14, see [findings 08](findings/08-head-detector.md)); face crops are NOT served — the pipeline must crop locally from originals using the returned boxes (validates the own-detector design); write-back fully supported (`PUT /people/{id}`, `PUT /people/{id}/reassign`, `PUT /faces/{faceId}`, `POST /faces` for manual face creation); API keys via `x-api-key` with fine-grained permission scoping (least-privilege read vs write keys possible).
- [Immich ML stack pinning](issues/02-immich-ml-stack-pinning.md): Immich's ML service contains no PyTorch at all — every model runs through ONNX Runtime (`onnxruntime>=1.23.2,<2`, Python 3.13, ARM64 images native with CPUExecutionProvider default). The goal.md constraint "same PyTorch version as Immich" is vacuous; the real compatibility constraints are the pinned `immich-model` git rev, the ONNX artifacts, and preprocessing.

- [Write-back semantics](issues/07-write-back-semantics.md): Confirmation writes via `POST /faces` — one face entry per cluster asset carrying a **head box** bound to the target person (person via `POST /people` only when new; anchor-less naming resolves against existing Immich people first, free text creates). Head boxes: Immich's own **unassigned** face detections preferred where contained in our person box (intersection/face-area ≥ 0.5, tunable) — `GET /faces` returns unassigned faces too, correcting an earlier note — else SCRFD-500M @320 on crops with geometric face→head expansion (weights vendored, ~2–6 s per 50-photo batch; YuNet is the clean-license fallback; [findings 08](findings/08-head-detector.md)); neither available → skip + flag in UI. Head detection is lazy at confirm time. Dry-run = zero Immich writes, proposals persisted locally, promotion replays (create person → faces). Different-person overlapping face → skip + flag, never overwrite. `(assetId, personId)` write ledger + check-before-write = idempotency; re-confirm is a no-op; manual removal in Immich → tombstone, never re-proposed. Write scope: all cluster members.

- [Confirmation UI shape](issues/06-confirmation-ui-shape.md): Variant **B (3-pane workspace)** wins, with A's config drawer folded in: sidebar queue → evidence grid (per-appearance status chips per ticket 07 + include/exclude checkboxes) → assignment pane with inline name prompt (existing-Immich-people autocomplete; existing → attach, new → create). Dry-run = top-bar toggle + mode banner + relabeled confirm; dry-run batches promote from a list. Tuning knobs in a ⚙ top-bar dropdown, rest in config file; store wipes stay out of the confirmation UI. Keyboard `j/k/c/s`. Prototype on throwaway branch `prototype/confirmation-ui` (primary source).
- [Re-ID model on ARM CPU](issues/03-reid-model-arm-cpu.md): OSNet/torchreid is viable on Pi 5 CPU — official aarch64 PyTorch wheels (2.12–2.15) work under uv out of the box, but the PyPI `torchreid` package is a stale third-party sdist dragging in TensorFlow-nightly: vendor `torchreid/models/osnet.py` (or BoxMOT's Re-ID module, AGPL-3.0) with weights baked into the image. Throughput: nano-YOLO detector ~7–15 img/s measured, osnet_x0.25 embedding ~50–100+ img/s estimated → a 50-photo nightly batch in ~10–30 s. Full ~30k backfill: 2–10 h (embedding-only via reused Immich detections: under ~2 h). Best alternatives: OSNet-AIN x0.25/0.5, HACNN. All estimates carry confidence levels in the findings file.
- [Model and detector selection](issues/04-model-and-detector-selection.md): Embeddings: `osnet_ain_x1_0` + **combineall** weights, 256×128 → 512-dim — the zoo has no ReID-trained `osnet_ain_x0.25` (fact-checked; only ImageNet init weights), and with a 30-min nightly budget the detector is the bottleneck, so the bigger AIN/combineall generalizer wins ([ADR 0001](../../docs/adr/0001-osnet-ain-x1-over-nano-osnet.md)). Vendored from torchreid (MIT), no BoxMOT. Detector: YOLO11n person-only, 640 input, on every asset; pixels from Immich preview thumbnails (~1440px), originals as fallback knob. Quality gates pre-embedding: confidence ~0.35 and min box height ~100px drop crops (logged per gate, thresholds = tuning knobs); edge-clipped persons kept. Granularity: one embedding per person-appearance (glossary created).
- [Clustering and anchoring rules](issues/05-clustering-and-anchoring-rules.md): Cosine distance over normalized embeddings; agglomerative average-linkage with configurable threshold (init 0.5, to calibrate); unfitted appearances stay singletons. A cluster is one person's appearance-group within one window — not a persistent identity, never merged across windows; window membership by EXIF capture time (local tz, upload fallback). Immich faces claim appearances by box containment; unanimous named anchor → propose for unlabeled appearances; any name disagreement → cluster blocked, surfaced as conflicted. Named anchors only in v1 (unnamed person-ID matching deferred as knob). Anchor-less clusters ≥2 appearances → ask-for-name queue (min size tunable, default 2). "Every cluster has an anchor" validated live via nightly window summary stats (anchored/conflicted/anchor-less %, singletons), not a dedicated exercise.
- [Batch container with checkpointed feed](issues/09-batch-container-checkpointed-feed.md): The feed is `POST /api/search/metadata` (`createdAfter`), not `POST /sync/stream` — Immich's sync endpoints reject API keys outright (403 "Sync endpoints cannot be used with API keys"; sync is session-token-only). Checkpoint (SQLite) persists the newest asset `createdAt` from a *fully completed* run and advances only after every page is fetched: crashed runs resume at-least-once, `createdAfter` is strictly-greater so completed assets are never re-served, and server-side timestamp comparison makes host clock skew irrelevant. Read-scoped `asset.read` API key; batch settings in `reid.toml`.
- [Person appearance embeddings](issues/10-person-appearance-embeddings.md): YOLO11n person-only via the `ultralytics` package (AGPL-3.0 accepted for private v1; ONNX/onnxruntime is the recorded permissive-distribution migration path, [ADR 0002](../../docs/adr/0002-ultralytics-runtime-for-yolo-detector.md)), `imgsz=640`, raw detections passed to our own ordered gates (conf floor 0.35 → min box height 100px → edge-clipped kept, per-gate drop counts logged; `conf=0.01` at the model so gates own the filtering). Pixels from Immich preview thumbnails, originals as fallback knob. Embeddings: vendored torchreid OSNet-AIN x1.0 + combineall weights (prefix-strip + strict load), 256×128 → 512-dim L2-normalized, deterministic for identical pixels. One appearance per detected person stored keyed `(asset_id, appearance)`; reprocessed assets replace rows idempotently. Wipe: separate `reid-wipe` console script (batch-run level, never in the confirmation UI) erases embeddings and resets the checkpoint — deliberate, so a changed detector/embedding config rebuilds the whole store.
- [Clustering and anchoring](issues/11-clustering-and-anchoring.md): every run re-clusters *all* stored appearances from scratch — pure `clustering.py` (cosine distance over re-normalized float32 embeddings, hand-rolled agglomerative average linkage cut at `distance_threshold`, no scipy; deterministic tie-breaks) and pure `anchoring.py` (face claims appearance at intersection/face-area ≥ `face_overlap`, best match wins; person-set claim = labeled, never proposed; empty person name labels without anchoring; unanimous named anchors propose for unlabeled members; ≥2 names → whole cluster conflicted; anchor-less clusters queue at `min_cluster_size`; singletons and below-minimum clusters get no rows). Window membership needs every appearance's capture time, so appearance rows persist `captured_at` resolved from `exifInfo.dateTimeOriginal`, falling back to `createdAt` (upload), converted to the container's local timezone; windows are blocks of ≤ `window_days` consecutive calendar days filled greedily from the earliest day (`partition_windows`, default 1 = same calendar day); appearances with unusable capture times are excluded from clustering (stored, never surfaced, warning logged) until a wipe rebuilds the store. Proposals persist per run in a `proposal` table `(asset_id, appearance, window, cluster, status, proposed_name)`, replaced wholesale each run, wiped by `reid-wipe`; the run echoes one summary line per window (clusters, anchored/conflicted/anchor-less %, singletons, proposals, ask-for-name). Stub Immich serves `GET /api/faces?id=`; tests use `distance_threshold = 0.01` since identical embeddings sit at float32-epsilon (~1e-7), nearest different fixture pair at 0.295.

## Not yet specified

<!-- see "Fog of war": in-scope fog you can't ticket yet; graduates as the frontier advances -->

- Manual backfill of the historical library: out of scope for v1 (see Out of scope); feasibility is now known — a full ~30k pass estimates at 2–10 h on the Pi 5, under ~2 h embedding-only via reused Immich detections. Returns as a fresh effort after v1.
- Scheduler mechanics: nightly run via cron/systemd timer vs a loop inside the container.
- Tuning knobs as they surface during use.
- Embedding/model versioning: what happens to stored embeddings when the embedding model or detector changes.

## Out of scope

<!-- work ruled beyond the destination; closed, never graduates -->

- Direct Immich integration (server-side); revisit after v1 works, possibly when open-sourcing.
- Video assets: photos only in v1.
- Multi-user support: single user.
- Automated on-upload triggering: manual/nightly batch only.
- Historical backfill in v1: existing photos are hand-labeled already; a manually triggered backfill is a later extension — feasible at 2–10 h for ~30k photos on the Pi 5 per [Re-ID model on ARM CPU](issues/03-reid-model-arm-cpu.md).

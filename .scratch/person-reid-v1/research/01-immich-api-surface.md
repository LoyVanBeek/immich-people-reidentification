## 1. Listing assets added since a given date

There are three viable mechanisms; the designed-for one for bulk/incremental consumers is the
**sync stream**.

### a) Metadata search — `POST /search/metadata` (`searchAssets`, stable since v2)

Body `MetadataSearchDto` (spec). Relevant date filters:

| Filter | Meaning |
| --- | --- |
| `createdAfter` / `createdBefore` | **"Date added to Immich"** — `AssetResponseDto.createdAt` is "The UTC timestamp when the asset was originally uploaded to Immich" |
| `takenAfter` / `takenBefore` | EXIF date taken (`fileCreatedAt` is the timezone-preserving original) |
| `updatedAfter` / `updatedBefore` | Asset-record update time (any modification, not just new uploads) |
| `trashedAfter` / `trashedBefore` | Trash time |

This is exactly the "nightly batch of new photos" filter: `createdAfter: <last run>`, plus
`type: IMAGE` (`AssetTypeEnum`), `visibility`, `libraryId`, etc. Other useful options:
`withPeople: boolean` ("Include people data in response"), `withExif`, `personIds` (filter by
person), `size` (default 250, **max 1000**). Pagination: `cursor` (string) is current;
`page`/`nextPage`/`total` are deprecated since v3.2.0 — use `SearchResponseDto.assets.nextCursor`
(and `count`), which also surfaces `facets`.

Response items are `AssetResponseDto` (id, type, checksum, originalFileName, `exifInfo`, `people`,
`stack`, visibility, `thumbhash`, dimensions...).

### b) Time buckets — `GET /timeline/buckets` + `GET /timeline/bucket`

`getTimeBuckets` groups assets into `YYYY-MM-DD` buckets (`count` + `timeBucket`); `getTimeBucket`
returns the assets of one bucket as columnar arrays (`TimeBucketAssetResponseDto`: parallel arrays of
`id`, `createdAt`, `fileCreatedAt`, `latitude`, `isImage`, ...). `orderBy` accepts `AssetOrderBy`
enum `takenAt | createdAt` — so "date added to Immich" is a first-class ordering.

Caveat: both endpoints carry `x-immich-state: "Internal"` in the spec — they are the timeline
endpoints the web/mobile clients use, but the spec flags them as internal rather than stable. For a
v1 pipeline prefer `POST /search/metadata` with `createdAfter`.

### c) Sync stream — `POST /sync/stream` (stable since v2)

The purpose-built incremental feed ("used by the mobile app to efficiently stay up to date with
changes" — `sync.controller.ts`). Body `SyncStreamDto { types: SyncRequestType[], reset? }`; response
is a JSON-lines stream (`application/jsonlines+json`). Relevant types from the `SyncRequestType`
enum: `AssetsV1`, `AssetsV2`, `AssetExifsV1`, `PeopleV1`, `AssetFacesV1`, `AssetFacesV2`,
`AssetFacesV3`. State is tracked via sync acknowledgements: `GET/POST/DELETE /sync/ack`
(checkpoints stored per session; delete acks to force a full re-sync). This gives new/changed
assets *and* face/person deltas without polling.

### Fetching pixels

`GET /assets/{id}/original` (`asset.download`, returns the untouched original) and
`GET /assets/{id}/thumbnail` (`asset.view`, with a `size` param) serve image bytes; both accept an
`edited` flag to get the edited version when the asset has edits.

## 2. Per-asset person/face detections and labels

What Immich stores per face is exactly a **bounding box + assigned person + source type**.

- `AssetFaceResponseDto` (spec, and `person.dto.ts` `AssetFaceResponseSchema`): `id`,
  `boundingBoxX1/X2/Y1/Y2`, `imageWidth`, `imageHeight`, `person: PersonResponseDto | null`,
  `sourceType` (`SourceType` enum: `machine-learning | exif | manual`).

How to get faces for an asset:

- **`GET /faces?id=<assetId>`** (`face.read`, stable since v2). Two important notes:
  - The OpenAPI parameter description says "Face ID", but this is misleading — the controller
    summary is *"Retrieve faces for asset"* and `person.service.ts#getFacesById` passes `dto.id`
    straight into `requireAccess(Permission.AssetRead, [dto.id])` and
    `personRepository.getFaces(dto.id)`: **the query parameter is the asset ID**, and the response is
    the array of that asset's faces (visible ones only: `isVisible: true`).
  - This is the *only* REST endpoint that returns bounding boxes. `AssetResponseDto.people` (on
    `GET /assets/{id}` and search results) is a **deduped list of `PersonResponseDto` only** —
    no boxes. Verified in `asset-response.dto.ts`: `people: z.array(PersonResponseSchema)` and
    `peopleFromFaces()` collapses faces to unique persons; the underlying `MapAsset.faces` never
    leaves the server except via `/faces` or the sync stream.
- **Sync stream**: `AssetFacesV3` sync rows carry the same fields plus `deletedAt` and `isVisible`
  ("Is the face visible in the asset"), with `personId: string | null` — so faces not yet assigned
  to any person are also reachable there (`SyncAssetFaceV1/V3` schemas).

What labels exist: `PersonResponseDto` = `id`, `name`, `birthDate`, `color`, `isFavorite`,
`isHidden`, `thumbnailPath`, `otherPeople`, sharing fields, `updatedAt`. People are paged via
`GET /people` (`PeopleResponseDto { total, hidden, hasNextPage, people }`; filters `name`,
`isHidden`, `withHidden`, `size`; `closestPersonId`/`closestAssetId` for similarity browsing), and
`GET /people/{id}`, `GET /people/{id}/statistics` (`{ assets }` count).

### Face crops

**No API endpoint serves an individual face crop.** The face-related binary endpoint that exists is
`GET /people/{id}/thumbnail` (`asset/octet-stream`, the person's *feature face* image — one crop per
person, chosen server-side). Immich *does* store a per-face crop internally, but only exposes it
through that person thumbnail indirection; there is no `GET /faces/{id}/thumbnail`. Consequence for
the pipeline: to get face crops for arbitrary detections, fetch the original (or a large thumbnail)
and crop locally using the face's bounding box — the boxes are in pixels relative to
`imageWidth`/`imageHeight` of the image version the face was detected on (see `mapFaces(face, edits,
assetDimensions)` in `person.service.ts`), so crop against the **original** at your own scale factor
or use a thumbnail with known dimensions.

The design assumption "we run our own person detector" stands: Immich gives you person-level face
detections with boxes and (sometimes) labels, plus full-resolution originals — nothing more.

## 3. Writing confirmed person labels back

Full read/write surface exists (all stable since v2):

| Action | Endpoint | Body | Permission |
| --- | --- | --- | --- |
| Create person | `POST /people` | `PersonCreateDto` (`name`, `birthDate`, `color`, `isFavorite`, `isHidden`) | `person.create` |
| Rename / update person | `PUT /people/{id}` | `PersonUpdateDto` (`name`, `featureFaceAssetId`, `isHidden`, `isFavorite`, `birthDate`, `color`) | `person.update` |
| Bulk rename/update | `PUT /people` | `PeopleUpdateDto` → `BulkIdResponseDto[]` | `person.update` |
| Assign a face to a person (naming a face) | `PUT /people/{id}/reassign` | `AssetFaceUpdateDto { data: [{ assetId, personId }] }` — bulk: all faces of the given asset(s) get person `{id}`... see note | `person.reassign` |
| Re-assign one face to another person | `PUT /faces/{faceId}` | `FaceDto { id: <faceId> }`, path id is the **target person** | `face.update` |
| Create a manual face (assign person to asset where ML found no face) | `POST /faces` | `AssetFaceCreateDto` = `{ assetId, personId, x, y, width, height, imageWidth, imageHeight }` | `face.create` |
| Delete a face | `DELETE /faces/{id}` | `AssetFaceDeleteDto { force? }` | `face.delete` |
| Merge people | `POST /people/{id}/merge` / `POST /people/merge` | `MergePersonDto` | `person.merge` |

Notes from the source:

- `POST /faces` ("Create a face … that has not been discovered by facial recognition. The content of
  the bounding box is considered a face") requires `AssetUpdate` on the asset and `PersonRead` on the
  person, and if the person has no feature photo yet the new face becomes it
  (`person.service.ts#createFace`). This is the documented write path for "this region is person X".
- `PUT /faces/{id}` (`reassignFacesById`): path `id` = target person, body `{ id: faceId }` = the
  face to move; it also updates the target person's feature photo if unset.
- `PUT /people/{id}/reassign` (`reassignFaces`, body `AssetFaceUpdateDto`) is the bulk variant the
  UI uses to move many faces onto one person; each `data[]` item is `{ assetId, personId }`.
- `PUT /people/{id}` additionally has a `PATCH` twin in the controller (`updatePersonV3`,
  `ApiExcludeEndpoint`, marked `v3PatchMigration`) — not part of the published spec.
- There is **no** endpoint to write back our own detector boxes as unlabelled faces
  (`personId` is required in `AssetFaceCreateDto`), and no endpoint to store embeddings.

## 4. Authentication: API keys and scoping

Three security schemes in the spec's `securitySchemes`, and every operation accepts
`bearer` OR `cookie` OR `api_key`:

| Scheme | Transport |
| --- | --- |
| `api_key` | **`x-api-key`** HTTP header (also accepted as `?apiKey=` query param — `ImmichHeader.ApiKey` / `ImmichQuery.ApiKey` in `server/src/enum.ts`) |
| `bearer` | `Authorization: Bearer <JWT>` (session/login token) |
| `cookie` | `immich_access_token` cookie (web client) |

(Heads-up: the docs once said `x-immich-api-key`; the working header is `x-api-key` — see immich
issue #22577 and the corrected docs.)

API key mechanics:

- Managed under `/api-keys`: `GET /api-keys` (list), `POST /api-keys` (create), `GET /api-keys/{id}`,
  `PUT /api-keys/{id}` (update), `POST /api-keys/{id}/rotate`, `GET /api-keys/me`.
  Requires `apiKey.create` / `apiKey.read` / `apiKey.update` / `apiKey.rotate` / `apiKey.delete`
  respectively (a key with `all` can self-manage keys).
- **Scoping is per-key, fine-grained**: `ApiKeyCreateDto` = `{ name, permissions: Permission[] }`
  (`minItems: 1`); `ApiKeyUpdateDto` re-sets `permissions`. The `Permission` enum has ~130 entries
  plus the wildcard `all`. Relevant to this pipeline: `asset.read`, `asset.view`, `asset.download`,
  `asset.statistics`, `face.read`, `face.create`, `face.update`, `face.delete`, `person.read`,
  `person.create`, `person.update`, `person.delete`, `person.statistics`, `person.merge`,
  `person.reassign`, `apiKey.read`, plus `timeline.read`, `sync.stream` and the
  `syncCheckpoint.read/update/delete` trio if the sync API is used.
- Every operation in the spec declares its required permission in `x-immich-permission`; the
  server enforces it via `isGranted` (`server/src/utils/access.ts`), where the key's permission list
  must contain the required permission or `all`. So a least-privilege key for a read-only nightly
  batch is possible (`asset.read`, `asset.download`, `face.read`, `person.read`), and the write-back
  component needs `face.update`/`person.update`/`person.reassign` etc.
- Keys are stored as SHA-256 hashes; the plaintext secret is returned exactly once at creation
  (`ApiKeyService`, `server/src/services/api-key.service.ts`). Keys act **as the owning user** —
  there is no cross-user delegation for a single-user instance; scoping is permission-based, not
  resource-based.
- api.immich.app (the official docs site, per the 2025-09-23 blog post "New API documentation") is
  the canonical rendered reference for authentication/authorization and per-endpoint permissions.

## Takeaways for the pipeline

1. **Nightly batch**: `POST /search/metadata` with `createdAfter` (= Immich upload time) + `type:
   IMAGE`, `size ≤ 1000`, cursor pagination; or `POST /sync/stream` (`AssetsV2`) + `POST /sync/ack`
   for a true incremental feed. `timeline/*` works but is spec-flagged `Internal`.
2. **Ground truth**: per-asset faces with boxes/labels via `GET /faces?id=<assetId>` (param is the
   asset id despite the spec's "Face ID" description) or `AssetFacesV3` sync rows. Asset responses
   only carry a deduped person list, no boxes.
3. **Crops**: not available over the API (except each person's feature-face thumbnail) — crop
   locally from originals using the returned pixel-space bounding boxes.
4. **Write-back**: supported and granular — rename via `PUT /people/{id}`, assign faces via
   `PUT /people/{id}/reassign` (bulk) or `PUT /faces/{faceId}`, and manual-face creation via
   `POST /faces`. Only requires an API key with the matching `face.*`/`person.*` permissions, which
   fits the "human confirmation before write-back" gate.
5. **Auth**: one key, `x-api-key` header (or `?apiKey=`), scoped with the `Permission` enum;
   least-privilege keys are a first-class feature.
